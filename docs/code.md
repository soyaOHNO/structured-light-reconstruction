# コードの読み方

## 1. この文書について

このプロジェクトのコードを読むための手引きです。**この文書を横に置きながらソースを読めば、どこに何が書いてあり、なぜそう書いてあるかが分かる**ことを目指しています。

手順書ではないので、操作方法は [measurement.md](measurement.md) と [reconstruction.md](reconstruction.md) を参照してください。

### 全体の構造

```
config/default.toml   すべての設定値。コードに数値を書かない
src/slr/              import して使う部品。単体では動かない
scripts/              直接実行するもの。番号順に実行する
tests/                実機なしで確認できる範囲の自動テスト
data/                 パターン・撮影画像・処理結果（Git 管理外）
```

**`src/` と `scripts/` の境界が設計の軸です。** `src/slr/` にあるものは必ず誰かから import される部品で、`scripts/` にあるものは必ず直接実行されるものです。この境界を保つと、同じ目的のコードが複数世代並んで「どれが使われているか分からない」状態を防げます。

`scripts/` のファイルは薄く作ってあります。引数を読み、設定を読み、`src/slr/` の関数を呼び、結果を表示するだけです。**処理の中身を知りたいときは `src/slr/` を読んでください。**

### データの流れ

```
config/default.toml
     │
     ├─→ patterns.build() ──────→ data/patterns/1920x1080/*.png
     │                                    │
     │   camera.Camera ─┐                 │
     │   projector.Projector ─┴─ capture.capture_sequence()
     │                                    │
     │                                    ↓
     │                            data/raw/<実験名>/*.png
     │                                    │
     ├─→ decode.decode_directory() ───────┤
     │        │                           │
     │        ↓                           │
     │   DecodeResult ──→ calibration.calibrate() ──→ calibration.json
     │        │                                              │
     │        └──────→ reconstruct.triangulate() ←───────────┘
     │                          │
     │                          ↓
     │                    PointCloud ──→ points.ply / evaluate / render
```

### 読む順序

1. **`config.py`** — すべての起点。他のすべてがこれを受け取る
2. **`patterns.py`** — 何を投影するのか
3. **`decode.py`** — 撮影画像から何を取り出すのか。**このプロジェクトの核心**
4. **`calibration.py`** — プロジェクタをどう「カメラ」として扱うのか
5. **`reconstruct.py`** — 対応から三次元へ
6. 残り（`camera.py`、`projector.py`、`capture.py`、`evaluate.py`、`render.py`、`cli.py`）は独立性が高いので、必要になったときに

## 2. 全体を貫く 3 つの決まりごと

個々のファイルを読む前に、全体で守っている規則を知っておくと理解が早くなります。

### 設定値はコードに書かない

解像度・露光・しきい値はすべて [config/default.toml](../config/default.toml) にあり、コードには定数として書きません。同じ値が複数箇所にあると、片方だけ直して食い違うからです。

実際、移植元のコードでは投影解像度が `options.ini`・撮影スクリプト・パターンのディレクトリ名の 3 か所に散らばっていて、全部直す必要がありました。

例外は「物理的に決まっていて設定する意味がないもの」だけです。たとえば `calibration.py` のサブピクセル探索窓は OpenCV の推奨値なので定数にしています。

### パスはプロジェクトルートから解決する

`config.find_project_root()` が `pyproject.toml` のある場所を探し、すべてのパスをそこからの相対で解決します。**カレントディレクトリに依存しません。** どのディレクトリから実行しても同じ場所を指します。

移植元では `../../FLIRpyspin/results/...` のような相対パスが使われており、実行ディレクトリを間違えると動きませんでした。

### 資源は with 文で確実に解放する

カメラ（`camera.Camera`）とプロジェクタ（`projector.Projector`）は `with` 文で使います。PySpin はカメラへの参照が残っているとシステムを解放できず、次回の起動に失敗します。例外が出ても必ず解放されるようにしています。

## 3. `src/slr/` の各モジュール

### config.py（155 行）

設定ファイルの読み込みと、パスの解決。

`Config.load()` が TOML を読み、セクションごとの dataclass に詰めます。dataclass はすべて `frozen=True` で、読み込み後に書き換えられません。設定が途中で変わると再現性がなくなるためです。

```python
config = Config.load()          # config/default.toml を読む
config.projector.size           # (1920, 1080)
config.pattern_dir              # data/patterns/1920x1080
config.raw_dir("test04")        # data/raw/test04
```

**`pattern_dir` が解像度をディレクトリ名に含めている**のが要点です。これにより、別解像度のパターンを誤って投影することが構造的にできません。

TOML のキーと dataclass のフィールド名は一致している必要があります（`**raw["camera"]` で展開しているため）。設定項目を増やすときは両方に追加してください。片方だけだと `TypeError` で落ちるので、黙って無視されることはありません。

### patterns.py（145 行）

グレイコードパターンの生成・保存・読み込み。

中身は OpenCV の `cv2.structured_light.GrayCodePattern` に任せています。生成される 44 枚は次の順序です。

```
pattern_00, pattern_01, ..., pattern_21   横方向（11 ビット × 2）
pattern_22, ..., pattern_43               縦方向（11 ビット × 2）
```

各ビットについて「パターン」と「その反転」が対になっており、先頭が最上位ビットです。**この並び順が `decode.py` の前提になっています。** 前提が崩れると結果は無意味になりますが、実写では「なんとなく歪んだ結果」として現れて気づけません。そのため [tests/test_decode_roundtrip.py](../tests/test_decode_roundtrip.py) で往復させて検証しています。

`save()` は画像と一緒に `manifest.json` を書きます。`load()` はそれを読み、**解像度が設定と食い違っていればそこで止めます。** 撮影を一巡させた後に気づくと丸ごとやり直しになるためです。

### camera.py（307 行）

FLIR カメラの制御。移植元の `capFuncs.py` を書き直したものです。

`Camera` クラスは `with` 文で使い、`open()` で設定を適用し、`start()`／`grab()`／`stop()` で撮影します。

**このファイルで最も重要なのは `_apply_settings()` です。** 構造化光のデコードは「投影した明るさと撮影された明るさが比例する」ことを前提にしているため、それを壊す設定をすべて無効化します。

| 設定 | 値 | 壊すとどうなるか |
| --- | --- | --- |
| `ExposureAuto` / `GainAuto` / `BalanceWhiteAuto` | Off | パターンごとに明るさが変わり、比較が成立しない |
| `Gamma` | 1.0 | 輝度の線形性が崩れ、大小比較が狂う |
| `PixelFormat` | BayerRG16 | デモザイクすると隣接画素が混ざり、境界がなまる |
| `StreamBufferHandlingMode` | NewestOnly | **投影パターンと撮影画像が 1 枚ずれる** |

最後の `NewestOnly` が特に厄介です。これがないとバッファに溜まった古いフレームを取得してしまい、結果を見ても原因が分かりません。設定できなければ例外で止めるようにしています。

`_grab_one()` では `GetNDArray()` の戻り値を `.copy()` しています。これは PySpin のバッファを参照しているだけで、`Release()` 後に内容が壊れるためです。移植元にはこの `copy()` がありませんでした。

`set_exposure()` は撮影中に露光を変えます。キャリブレーションで、部屋の照明（暗い）とプロジェクタ（明るい）を切り替えるのに使います。露光を伸ばす前にフレームレートを下げているのは、フレームレートが露光時間の上限を縛るためです。

### projector.py（147 行）

Tkinter と Pillow による全画面投影。

`mainloop()` を使わず、`show()` のたびに `update()` を呼んでいるのが特徴です。**撮影ループから同期的に駆動する**ためで、イベントループに制御を渡してしまうと「表示してから撮る」という順序を保証できません。

`position` プロパティが表示位置を決めます。`auto = true` のとき `GetSystemMetrics(0)`（メイン画面の幅）を X オフセットにして、プロジェクタをメイン画面の右隣として扱います。

移植元は pygame の `FULLSCREEN` を使っており、これは必ずメインディスプレイに出るため「プロジェクタをメインスクリーンにしてください」という制約がありました。Tkinter で座標指定にすることで、プロジェクタを 2 画面目のまま使えます。

`_photo` に `PhotoImage` の参照を保持しているのは、参照が切れるとガベージコレクトされて画面が真っ白になるためです。Tkinter でよくある落とし穴です。

### capture.py（119 行）

投影と撮影の共通処理。計測用の撮影（`02_capture.py`）とキャリブレーション用の撮影（`04_capture_calibration.py`）の両方から使われます。

`capture_sequence()` は「表示 → 待機 → 撮影 → 保存」を繰り返すだけです。待機（`warmup_sec`）は、プロジェクタが切り替わり、その明るさで露光が一巡するのを待つためのものです。

撮影画像はパターンと同じファイル名で保存します。デコード時に名前で対応づけられるようにするためです。

`save_metadata()` が撮影条件を JSON で残します。「どの露光で撮ったか」を画像だけから復元するのは困難なので、必ず一緒に保存します。

### decode.py（315 行）

**このプロジェクトの核心です。** 撮影画像列から、カメラ画素ごとのプロジェクタ座標を復元します。

OpenCV にも `getProjPixel()` がありますが、1 画素ずつしか扱えず、200 万画素を Python のループで回すと現実的な時間で終わりません。そのため numpy で書き直しています。

処理は `decode_arrays()` に集約されています。読む順序は次のとおりです。

**1. 画素ごとの振れ幅を求める**

```python
span = white - black          # その画素が取りうる明るさの幅
shadow_mask = span >= mask_threshold * full_scale
```

影になっている画素や投影光が届かない背景は、ここで落ちます。

**2. ビットごとに大小を判定する**（`_decode_axis`）

```python
difference = normal - inverted        # パターンと反転パターンの差
bits.append(difference > 0)           # 符号がビットの値
reliable &= np.abs(difference) >= bit_threshold * scale
```

**しきい値が絶対値ではなく `scale`（その画素自身の振れ幅）に対する比**なのが要点です。相対値にすることで、対象の反射率、レンズ周辺の減光、Bayer 配列の色ごとの感度差を吸収できます。絶対値で判定していたときは Bayer の位相によって有効率が偏り（赤 39.8% / 緑 30.6%）、プレビューに規則的な格子模様が出ていました。

なお撮影画像は Bayer の RAW のまま扱います。各ビットの判定は「同じ画素のパターンと反転パターンの比較」なので、色フィルタの感度差は引き算で打ち消し合うためです。

**3. グレイコードを 2 進数に戻す**（`_gray_to_binary`）

```python
current = previous XOR bits[i]    # 最上位から順に
value = (value << 1) | current
```

**4. 使わないビットの処理**

`skip_fine_bits` が 1 以上なら、末尾（細かい側）のビットをその数だけ使いません。縞幅が 1〜2 投影画素になるパターンは光学的に解像できず、使うと画素が大量に無効になるためです。飛ばした分だけ桁を戻し、そのブロックの中心を採ります。

```python
value = (value << skip) + (1 << (skip - 1))
```

**5. 範囲外を落とす**

復号した座標が投影解像度の外に出た画素は、判定を誤っています。

`bit_reliability()` は診断用で、ビットごとの通過率を測ります。`skip_fine_bits` をいくつにすべきかを実測で決めるためのものです。

### calibration.py（317 行）

カメラとプロジェクタの内部パラメータと、両者の相対姿勢を求めます。

**考え方: プロジェクタは「光を投げるカメラ」です。** 平面のボードにグレイコードを投影して撮影すると、ボード上の各交点がプロジェクタのどの画素から照らされていたかが分かります。これを「プロジェクタが撮影した交点の座標」とみなせば、カメラと同じ手順で校正でき、さらに両者をステレオ対として外部パラメータを求められます。

読むべき関数は 3 つです。

**`detect_corners()`** — 全白画像から交点を検出します。`to_display()` で RAW を 8bit に落としてから `_find()` を呼びます。

`to_display()` の正規化は上下 1% を除いた範囲で行います。最小値と最大値で正規化すると、投影光の鏡面反射のような一点の極端な輝度に引きずられ、ボードのコントラストが狭い範囲に潰れてしまうためです。

`_find()` は 3 段階で試します。`findChessboardCornersSB`（照明むらとぼけに強い）→ CLAHE で補正してから同じもの → 従来の `findChessboardCorners`。

**`projector_corners()`** — カメラ画像上の交点を、プロジェクタ画像上の座標へ移します。**このファイルで最も重要な関数です。**

デコード結果は投影画素単位（`skip_fine_bits = 2` なら 4 画素単位）に量子化されているので、交点をそのまま対応づけると精度が出ません。しかしボードは平面なので、カメラ座標とプロジェクタ座標は射影変換で結ばれます。そこで交点のまわり ±`corner_window` にあるデコード済み画素から射影変換を RANSAC で当てはめ、交点のサブピクセル位置を移します。

合成データでは、既知の変換を 0.012 画素の誤差で復元できています（[tests/test_calibration.py](../tests/test_calibration.py)）。

**`calibrate()`** — `cv2.calibrateCamera()` をカメラとプロジェクタそれぞれに適用し、`cv2.stereoCalibrate()` で相対姿勢を求めます。ステレオの段階では `CALIB_FIX_INTRINSIC` を指定し、内部パラメータは固定したまま相対姿勢だけを推定します。

`board_object_points()` が返すのは、ボード座標系での交点の三次元位置（Z = 0 の平面）です。**ここで mm 単位の実寸を与えることで、復元結果が実スケールになります。**

### reconstruct.py（270 行）

対応マップとキャリブレーション結果から三次元点群を作ります。

`triangulate()` の流れは次のとおりです。

```python
# 1. 有効画素の、カメラ座標とプロジェクタ座標を並べる
camera_pixels    = [[x, y], ...]
projector_pixels = [[proj_x, proj_y], ...]

# 2. レンズ歪みを除き、焦点距離で割った正規化座標にする
cv2.undistortPoints(...)

# 3. カメラを原点、プロジェクタを [R|T] に置いて交点を求める
cv2.triangulatePoints(P_camera, P_projector, ...)

# 4. 同次座標を戻し、奥行きと再投影誤差で絞り込む
```

内部パラメータは `undistortPoints()` で既に取り除かれているので、投影行列には含めません（`_projection_matrices()` が単位行列と `[R|T]` を返すのはそのためです）。

`_reprojection_errors()` は、求めた点を両方の像に投影し直して元の画素とのずれを測ります。**2 本の光線がきれいに交わらなかった点ほどこの値が大きくなる**ので、対応を誤った画素を落とせます。

`write_ply()` はバイナリ形式の PLY を書きます。numpy の構造化配列をそのままバイト列にしており、1 点あたり 15 バイト（座標 12 + 色 3）です。numpy は構造化 dtype にパディングを入れないので、この前提が成り立ちます。

### evaluate.py（234 行）

既知形状との比較による精度評価。

`fit_plane()` と `fit_sphere()` はどちらも RANSAC で外れ値を除いてから当てはめ直します。指定した範囲に計測対象以外のもの（背景や台）が混ざっていても、少数派として除外されるためです。

`_fit_plane_least_squares()` は主成分分析による直交回帰を使っています。`z = ax + by + c` の形で解くと、平面がカメラの視線と平行に近いときに破綻するためです。重心まわりの分散が最も小さい方向を法線とすれば、どの向きの平面でも同じ精度で扱えます。

球の当てはめは線形最小二乗で解けます。`|p - c|² = r²` を展開すると `|p|² = 2c·p + (r² - |c|²)` となり、`c` と `(r² - |c|²)` について線形だからです。

**平面と球は検出できる誤差の種類が違います。** 平面は残差の広がり（ばらつき）を、球は直径の実測値との比較でスケールの系統誤差を捉えます。

### render.py（119 行）

点群の描画。外部ライブラリを使わず numpy だけで実装しています。

奥から順に描く画家のアルゴリズムで、手前の点が奥の点を上書きします。

```python
order = np.argsort(-depth)    # 奥が先、手前が後
```

倍率は重心からの最大距離を基準に決めます。**どの向きから見ても画面に占める大きさが変わらない**ようにするためです。

`turntable()` が視点を一周させず左右に振るのは、構造化光で得られるのが片側から見た表面だけで、裏側には点がないためです。真横を越えると形が分からなくなります。

### cli.py（22 行）

スクリプト共通の実行ラッパー。

設定ミスや機材の未接続は実験中に日常的に起きるので、`FileNotFoundError` / `ValueError` / `RuntimeError` を捕まえて一行のメッセージにします。**それ以外の例外はそのまま送出します。** 想定外の不具合の情報を握りつぶさないためです。

## 4. `scripts/` の各スクリプト

`scripts/` は薄く作ってあるので、処理の中身は `src/slr/` にあります。ここでは「そのスクリプト固有の判断」だけを説明します。

| スクリプト | 固有の判断 |
| --- | --- |
| `00_check_hardware.py` | カメラとプロジェクタを個別に確認できるよう `--camera-only` / `--projector-only` を持つ |
| `01_generate_patterns.py` | 既存のパターンは `--force` なしに上書きしない |
| `02_capture.py` | 既存の実験名には追記せずエラーで止める。条件の違う画像が混ざるのを防ぐため |
| `03_decode.py` | `--bits` で診断を出す。有効画素が 1% 未満なら原因の候補を表示する |
| `04_capture_calibration.py` | 最も複雑（341 行）。下記参照 |
| `05_calibrate.py` | 不完全な姿勢は飛ばして続行する。`--probe` で交点数を実測できる |
| `06_reconstruct.py` | 撮影画像の解像度が校正時と違えばエラーで止める |
| `07_evaluate.py` | `--roi` を画面上の座標で指定する。`depth.png` を見ながら決められるようにするため |
| `08_render.py` | 静止画と GIF の両方を出す。静止画だけでは奥行きが分からないため |

### 04_capture_calibration.py が複雑な理由

このスクリプトだけ 341 行と大きいのは、**失敗を前提にした作りになっている**ためです。次の 4 つを順に行います。

**1. 不完全な姿勢の掃除**（`survey_poses`）— 必要な画像が全部揃っているかを実際に確認します。ディレクトリの数だけを数えると、途中で中断した姿勢も「撮影済み」と見なしてしまい、二度と埋まりません。

**2. 撮影前の検出確認**（`capture_board`）— パターン一式の撮影には 1 分近くかかるため、その前に 1 枚だけ撮って交点を検出できるか確かめます。失敗しても数秒で分かります。

**3. 露光の自動調整**（`suggest_exposure`）— 検出できなければ露光を変えて撮り直します。上位 0.5% 点がフルスケールの 60% に来るよう計算し、1 回の変更幅は 8 倍までに制限しています。**成功の判定は明るさではなく「交点を検出できたか」です。** 暗くてもコントラストがあれば検出できるためです。

**4. 失敗時の診断**（`diagnose`）— 検出に使った画像と RAW を保存し、どの交点数なら検出できたかを総当たりで調べます。設定と違えば「`columns = 8` にしてください」と具体的に表示します。

## 5. テストの考え方

`tests/` にあるのは、**実機なしで確認できる範囲**のテストです。カメラやプロジェクタを使う部分は対象外です。

テストの狙いは「目で見ても正しさが分からない処理」を機械的に確かめることです。

| テスト | 何を確かめているか |
| --- | --- |
| `test_decode_roundtrip.py` | 生成したパターンを完全な撮影画像とみなして復号し、元の画素位置と一致するか。**パターンの並び順の前提が崩れていないか**を検証している |
| `test_calibration.py` | 合成したチェッカーボードで交点が検出できるか。既知の射影変換を `projector_corners()` が復元できるか |
| `test_reconstruct.py` | 既知の平面を既知のカメラ・プロジェクタに投影し、三角測量で元の座標に戻せるか |
| `test_evaluate.py` | 既知のノイズを与えた形状から、そのノイズの大きさを取り戻せるか |
| `test_render.py` | 視点を変えたときに見え方が変わるか。手前の点が奥の点を隠すか |

**三角測量とデコードは、間違っていてももっともらしい結果が出ます。** 歪んだ点群や、なんとなく滑らかな対応マップが得られてしまい、目視では判断できません。だから数値で確かめています。

実行方法は [README.md](../README.md) の「テスト」を参照してください。

## 6. 設定項目を増やすとき

設定を 1 つ増やすには、3 か所に手を入れます。

1. [config/default.toml](../config/default.toml) に値とコメントを書く（**なぜその値なのかも書く**）
2. [src/slr/config.py](../src/slr/config.py) の対応する dataclass にフィールドを足す
3. 使う側のコードで `config.<セクション>.<項目>` として参照する

TOML と dataclass が食い違うと `TypeError` で落ちるので、片方を忘れても黙って無視されることはありません。

## 7. 処理を 1 段追加するとき

たとえばメッシュ化を足す場合は次のようにします。

1. `src/slr/mesh.py` に処理を書く（引数は `Config` と、前段の結果）
2. `scripts/09_mesh.py` を作り、引数を読んで `src/slr/mesh.py` を呼ぶだけにする
3. `tests/test_mesh.py` に、合成データで正しさを確かめるテストを書く
4. 設定が必要なら `config/default.toml` と `config.py` に足す
5. [README.md](../README.md) のコマンド一覧と [reconstruction.md](reconstruction.md) の手順に追記する

**新しいトップレベルのディレクトリは作りません。** 部品は `src/slr/`、実行するものは `scripts/` という境界を保ちます。
